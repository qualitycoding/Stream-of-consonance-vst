| R-001 | Fixtures gave `cents` with no stated reference pitch. An implementer converting with C4 (261.6255 Hz) instead of A3 (220 Hz) gets a silently wrong roughness term — up to 0.082 score units — and a stream that drifts off target with nothing raising. | Invalid research assumption / implementer misinterpretation | **Critical → closed** | Was high: the model file itself defines `REF_HZ = C4`, which is the obvious constant to reach for | Two different reference pitches coexist in the model for different purposes | C-002, C-005, all fixtures | `make_fixtures.py` now writes `ref_hz` plus an explicit note into every fixture; **T-000** asserts every fixture declares it; `soc_core.h` documents both constants and why they differ. | R-002 | Generation cannot keep ahead of the note clock on the target machine, producing audible gaps. | Scale and performance | **High → Medium** | Medium — sandbox timings are not target timings | The model is 600 ms/note in Python free mode; the C++ speedup factor is assumed, not measured on target | C-012, D-002, S-010 | Generator thread plus lookahead queue; T-013 enforces a 40 ms budget; T-019 is a 30-minute soak; D-002 defines a resolution ladder; underrun degrades to a repeated note rather than silence, with a visible counter. |
| R-003 | JUCE drifts to 9.x mid-project (by a teammate, a fresh clone, or a submodule update) and the VST3 client API changes under the plugin. | Dependency and supply-chain drift | **High → Medium** | Medium | `D:/JUCE` is a shared working copy, not a pinned submodule | C-013, C-014, D-001 | S-002 records and verifies the exact JUCE commit SHA into the checkpoint; D-001 forbids a silent 9.x upgrade and classifies it as a Phase 0 scope change. |
| R-004 | The VST3 parameter list changes between plugin versions (e.g. removing `Start Frequency` when in Note mode), orphaning users' saved automation lanes. | Technical correctness / operational | **High → closed** | Was medium — it is the natural first implementation | VST3 forbids changing the parameter list after instantiation | D-007, S-009 | D-007 makes both start parameters permanent and always automatable; the editor greys rather than removes; S-015 checks a save/reload cycle. |
| R-005 | Plugin-level tests T-015 … T-020 are specified but were never red-verified, because JUCE is not installable in the planning sandbox. A test that cannot fail proves nothing. | Implementer misinterpretation | **High → Medium** | Certain (it is a known gap, not a possibility) | Planning environment lacks JUCE and a DAW | S-009, S-015 | The 15 **core** tests were genuinely compiled and red-verified (`spike_03_red_verify_output.txt`). | R-006 | Ableton may not honour MPE zone configuration (RPN 6) or bend-range (RPN 0,0) emitted from a plugin's MIDI output, so downstream pitches are wrong by a factor of 24. | Operational reality / invalid assumption | **Medium** | Medium | C-015 is single-source; the Ableton FAQ documents MPE *input* and clip editing, not plugin MIDI *output* | C-015, D-006, S-012 | S-012's failure rule forbids silently switching to ±48; it requires surfacing a Bend Range control and logging. | R-007 | JUCE is AGPLv3-or-commercial. | R-008 | Invalid input (empty chord, non-positive or non-finite frequency) is scored silently in C++ where Python raises, producing NaN deep inside a stream. | Technical correctness | **Medium** | Medium — C++ will not raise on its own | Validation lives in `_validate()` in Python and is easy to omit when porting | C-002, S-004 | T-007 asserts all three cases throw; it is written so that a not-implemented stub still fails rather than accidentally passing. |
| R-009 | The synth's timbre drifts from the scorer's (e.g. someone adds a filter or a different partial count), so the consonance number stops describing what is audible. | Technical correctness | **Medium** | Low | The Python model guards this with `check_timbre`; the port could omit it | C-001, D-003, S-011 | S-011 requires a construction-time assertion that the synth timbre equals the scorer timbre, mirroring `CompositeModel.check_timbre`. |
| R-010 | Bounces are not reproducible because the note clock accumulates samples instead of following the host's ppq position across loops and locates. | Operational | **Low** | Medium | A sample counter is the simpler implementation | A-007, S-013 | S-013 mandates ppq-derived timing and an RNG reset on transport start; T-018 compares two bounces sample-for-sample. |
